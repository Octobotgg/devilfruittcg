## PART 1: WHAT IS THIS PROJECT?

### The Big Picture

This is a fan-made website for the **One Piece Trading Card Game** called **DevilFruit TCG**. Think of it as a one-stop shop for One Piece card game players — they can look up cards, check market prices, track their collection, build decks, and see what's winning in tournaments.

It's a full web application, not a simple website. There's a server running behind the scenes that fetches live pricing data from eBay, stores user collections in the cloud, and crunches tournament statistics.

### What It's Built With

The site runs on **Next.js 15** (a popular web framework made by Vercel) using **TypeScript** (a safer version of JavaScript). Styling is done with **Tailwind CSS v4**. It uses two cloud services for user accounts — **Supabase** handles real logins (email/password) while **Firebase** handles anonymous sessions (looks like a migration in progress). Card animations use **Framer Motion**, price charts use **Recharts**, and the whole thing deploys to **Vercel** automatically when code is pushed to git. There's also a local **SQLite** database for development.

### How the Folders Work

Here's what each top-level folder does:

**`app/`** — This is where all the pages and server endpoints live. Each subfolder is a page on the website (like `/market`, `/collection`, `/deckbuilder`) or a behind-the-scenes API endpoint (like `/api/cards`, `/api/market`). The `layout.tsx` file here is the "shell" that wraps every page with the navbar and footer.

**`components/`** — Reusable building blocks shared across pages. The navbar, card modals, market panels, buttons, and visual effects all live here. Think of these like Lego pieces that get assembled on different pages.

**`lib/`** — The brain of the app. This is where all the logic lives: how cards are loaded and searched, how market data is processed, how user authentication works, how themes are applied, and so on. This folder is also where the biggest mess is (more on that below).

**`data/`** — The card database. The main file is `bandai-en-official-cards.json`, which contains every card from the official Bandai catalog. Other files here are audit snapshots used for quality checks.

**`scripts/`** — Maintenance tools you run manually. The most important one (`fetch-bandai-official-en.mjs`) pulls fresh card data from Bandai's website. Others validate data consistency or run smoke tests.

**`public/`** — Images and SVGs served directly to browsers. Background textures, logo concepts, and (currently) a bunch of unused leftover files from the Next.js starter template.

**`reports/`** — Audit reports generated by the data-checking scripts.

### The Pages Users See

The site has 15 pages: a **homepage** with featured cards and live tickers, a **card market** for browsing and searching all cards with pricing, individual **card detail** pages with price history, a **collection tracker**, a **deck builder** and **saved decks** archive, a **meta snapshot** showing top competitive decks, a **matchup matrix** for deck-vs-deck stats, **match history** search, **account** and **login** pages, **privacy** and **terms** pages, plus two experimental pages (**logo lab** and **theme lab**) for testing designs.

### How Card Data Flows Through the App

The pipeline is straightforward: a script fetches card data from Bandai's official website and saves it as a big JSON file. A TypeScript module (`lib/official-cards.ts`) reads that JSON and makes it searchable. A wrapper layer (`lib/card-feed.ts`) adds pagination. API endpoints serve this data to the pages, and users see the cards in their browser.

The `Card` type definition — the blueprint that describes what a card object looks like — lives in `lib/cards.ts` and is imported by almost every file that touches card data.

## PART 2: PROBLEMS FOUND

I verified every finding independently against the actual codebase. I found one **error in the previous audit**: it marked `lib/cards.ts` as safe to delete, but that file defines the `Card` type interface which is imported by 10+ active files including `official-cards.ts`, `card-feed.ts`, `market-catalog.ts`, `ebay.ts`, `card-variants.ts`, multiple pages, and API routes. **It must be kept.**

### Category A — Legacy Per-Set Card Files (37 files, safe to delete)

When the project started, each card set was hand-typed as a separate TypeScript file. This was replaced by the single official Bandai JSON catalog. The old files are still sitting in `lib/` but nothing imports them anymore.

**The real current source:** `data/bandai-en-official-cards.json` → `lib/official-cards.ts`

**Safe to remove:**

- `lib/op01-cards.ts` through `lib/op14-cards.ts` (14 files — main booster sets)
- `lib/st01-cards.ts` through `lib/st21-cards.ts` (21 files — starter decks)
- `lib/eb01-cards.ts` and `lib/eb02-cards.ts` (2 files — extra boosters)

**Verified:** Zero imports found for any of these 37 files in active code. They only import *from* `lib/cards.ts` (the type), but nothing imports *them*.

### Category B — Legacy Support File (1 file, safe to delete)

- `lib/starter-decks.ts` — This file referenced the old ST-series files above. With those files gone, this serves no purpose. Zero imports found.
